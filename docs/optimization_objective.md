# 第一步：优化目标与验收标准

状态：首轮分析的工作约定；尚未实施优化或验证加速。

## 1. 项目要求与当前范围

课程依据：`docs/L2_Project.pdf` 第 7、10 页。

- 项目目标：构建自动优化 agent 生成的 Python ML 流水线的系统，在保持预测质量的同时减少执行时间。
- 主要评估指标：trajectory speedup，以及 trajectory 中最佳验证分数相对基线的变化（在指定容差内）。若优化使用 LLM，需要报告其推理时间。
- 最终评估要求：10 条固定 trajectory（5 条提供、5 条收集），每条至少 20 个 pipeline。
- 当前第一轮只分析 `spaceship_titanic_students`：7 个步骤、25 个候选。单条 trajectory 的结果不能代表最终系统的普遍收益。

## 2. 本轮研究问题

在保留当前固定候选工作负载和步骤依赖的前提下，哪些优化方向最有可能缩短完整 trajectory 的端到端墙钟时间？已有证据有多强，还需要什么实验才能验证？

本轮分析的交付物是有证据支持的优化优先级，不是立即选择某种技术，也不是宣称已经加速。

## 3. 指标与计时边界

| 指标 | 定义与用途 |
| --- | --- |
| 主要指标：端到端时间 T | 从启动执行入口之前开始，到全部候选结束、最终汇总写出且入口退出为止；包括启动、导入、读写、预处理、训练、预测及调度开销 |
| 加速比 S | 同一输入和资源预算下，T_baseline / T_optimized；重复运行后采用同一种汇总方式计算并报告波动 |
| 预测质量 Q | 所有固定候选的 pooled out-of-fold accuracy 的最大值；与基线比较 |
| 辅助指标 | 候选运行时间、阶段热点、内存与 CPU 使用；用于解释原因和资源代价，不替代端到端指标 |
| 优化开销 | 单独记录分析、改写、编译、缓存构建等耗时；分别报告首次端到端成本与可复用后的成本。使用 LLM 时单列推理时间 |

基线是原始顺序执行方式。最终时间比较使用未启用 profiler/tracer 的运行；已有 profile 用于定位与估算，不能直接作为优化后的实测基线。

缓存的首次构建计入首次运行；热缓存结果单独报告。对比固定数据、代码版本、依赖、硬件、线程与资源预算，避免将缓存状态或测量工具的差异当作优化收益。

## 4. 首轮优化边界

执行依据：`spaceship_titanic_students/trajectory.json` 和 `run_trajectory.py`。

- 保留全部 25 个候选的逻辑评估与输出，不通过删除候选获得加速。
- 保留步骤间屏障；同一步内允许调整执行顺序和并发。
- 首轮保持数据、特征定义、模型超参数、三折划分和随机种子不变。
- 允许验证等价后复用中间计算或预测；复用必须满足原有步骤约束，并保留各候选输出。
- 折内拟合的预处理器只能在训练行、输入、参数等一致时复用，不能把验证数据引入拟合。

这些是本轮便于隔离系统优化效果的工作约束，不是课程禁止算法替换或其他优化。

## 5. 验收口径

课程层面：最佳验证分数应在预先指定的容差内保持。课程材料未给出具体数值，不将自定数值表述为课程规定。

首轮采用更严格的工作目标：

1. 所有候选完成，输出字段、行数、PassengerId 和 fold 对齐。
2. 比较逐行概率，报告最大绝对误差；开始优化实验前确定并固定数值容差。
3. 检查阈值判定、各候选准确率与排名是否保持；不能只凭概率误差很小认定阈值结果相同。
4. 在相同资源预算下重复测量端到端时间，报告中位数与波动；一次运行更快不足以证明稳定收益。
5. 报告资源需求和优化本身的开销，不预设未经证据支持的加速百分比。

当前待实验设计阶段确定：概率比较容差、运行次数、硬件/线程预算。此阶段不填写虚构的基线时间或实验结果。
